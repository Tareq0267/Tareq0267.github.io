Lesson 0

The big picture

You already know the pipeline: sensors → black magic → effectors. This lesson opens up the black magic.

Goals

  • Map every part of the project onto sensors → policy → actuators.
  • Know the three things you design when you create a task.
  • Know which layer each buzzword belongs to.

1. The deployed robot: what runs at 50 Hz

SENSORS POLICY ("black magic") EFFECTORS ─────── ────────────────────── ───────── IMU (tilt, spin rate) ┐ joint encoders (31) ├──► obs: 102–109 numbers ──► neural ──► 31 numbers ──► PD control ──► motors camera → ball position ┘ network (target angles) (in each joint) this loop runs every 0.02 s (50 Hz)

The policy is a small neural network: three hidden layers (256 → 128 → 128 neurons), about 84,000 numbers called weights. Running it is a handful of matrix multiplications, which takes microseconds. There is no hidden logic in it, no "if ball then move leg". The behaviour lives entirely in the values of those 84k numbers.

The output is not torque. It's 31 target angles, one per joint, written as offsets from a default standing pose. A PD controller inside each joint then pushes toward that target. This is safer and much easier to learn than raw torque.

ROS analogy

The deployed policy is a single node: it subscribes to /imu, /joint_states and /ball_detection, runs action = policy(obs), and publishes /joint_position_targets at 50 Hz. Training is how you get the weights inside that node.

2. Where the weights come from: training in simulation

You can't learn by trial and error on the real robot. It would fall thousands of times. So you build a fake world (a physics simulator), drop thousands of virtual robots into it, and let them practise:

repeat billions of times: 1. each robot sees its obs, the network picks an action (slightly random → exploration) 2. physics advances 0.02 s 3. YOU compute a reward: one number, "how good was that?" 4. every few steps: adjust the 84k weights so high-reward actions become more likely

The learning algorithm (PPO), the neural network and the GPU simulation are reusable machinery. Most of your creative work is in this table.

Lesson 1

Reinforcement learning in plain language

The vocabulary, the loop, and a goalkeeper you can run in 30 lines of plain Python.

Goals

  • Use agent, environment, observation, action, reward, episode, return, discount, policy and value correctly.
  • Compute a discounted return by hand.
  • Run a toy goalkeeper environment and compare two policies.

2. Return and discount: what the agent maximizes

The agent doesn't maximize the reward of this step. It maximizes the return: the sum of all future rewards, with later ones counted a bit less:

G_t = r_t + γ·r_{t+1} + γ²·r_{t+2} + γ³·r_{t+3} + … (γ = "gamma" = discount, 0.99 here)

Worked example. Rewards [1, 1, 1, 10], γ = 0.9:

G = 1 + 0.9·1 + 0.81·1 + 0.729·10 = 1 + 0.9 + 0.81 + 7.29 = 10.0

Why discount? It sets a horizon: how far ahead the agent effectively cares. A handy rule of thumb is horizon ≈ 1 / (1 − γ). With γ = 0.99 that's about 100 steps, and at 50 Hz that is about 2 seconds. A goalkeeper save happens within about 1–1.5 s of a shot, so this horizon fits.

Why it matters

If a good outcome comes much later than the horizon, the agent hardly "sees" it. That's one reason we add shaping rewards that pay off now for progress toward something good later (Lesson 8).

3. Policy and value

  • Policy π(a | o): given what I see, which action do I take? During training it's a probability distribution (it explores). At deployment we take its most likely action.
  • Value V(o): from here, how much return do I expect? This is a second network, the critic. It never controls the robot; it only helps training judge whether an action turned out better or worse than expected (Lesson 2).

4. Hands-on: a 1-D goalkeeper

A keeper slides along the goal line. Each episode, a shot will cross the line at a random target. The keeper sees obs = target − x ("how far is the ball's line from me?") and chooses left, stay or right. The reward is −|target − x| every step, so being closer is less bad.

Lesson 2

How learning works: from "try things" to PPO

The idea is simple: do more of what turned out better than expected. Everything else is engineering to make that stable.

Goals

  • Explain policy gradient, advantage and the critic in one sentence each.
  • Know what PPO's clip, entropy, GAE and adaptive learning rate are for.
  • Read the batch numbers (4096 × 24, 4 minibatches, 5 epochs).
  • Watch a 6-number policy learn the toy keeper.

1. A network is a function with knobs

A neural network is action_distribution = f(obs; W), where W are the knobs (weights). "Learning" means turning the knobs so good actions get more probable. For the T2 policy:

obs (102) → 256 → 128 → 128 → 62 outputs (31 means + 31 spreads for the 31 joints) weights ≈ 102·256 + 256·128 + 128·128 + 128·62 (+ biases) ≈ 84,000

Training samples each action from a Gaussian with those means and spreads, then squashes it with tanh into [−1, 1] (a "tanh-normal" distribution). The env multiplies by action_scale (0.5 for standing) to get radians.

2. Policy gradient: the core idea

for each action taken: push log π(action | obs) UP by an amount ∝ advantage (advantage > 0: better than expected → more likely) (advantage < 0: worse than expected → less likely)

Advantage = what actually happened − what the critic expected. Using "better than expected" instead of raw return is crucial. If every return is negative (as in the toy keeper), raw returns would push every action down. Advantages separate the good actions from the bad ones.

One-step version (TD error):

δ = r + γ·V(next) − V(now) example: r = 1, V(now) = 5, V(next) = 6, γ = 0.99 → δ = 1 + 5.94 − 5 = 1.94 > 0 → "better than expected"

GAE (Generalized Advantage Estimation, gae_lambda = 0.95) blends one-step, two-step, … estimates of the advantage. That reduces noise while staying mostly unbiased. You don't need its formula, just what it's for.

3. Hands-on: watch a policy learn

This is REINFORCE, PPO's ancestor, learning the toy keeper from Lesson 1. The whole brain is a 3×2 matrix W: for each action, logit = w_obs · obs + w_bias.

Typical output: the return climbs from about −12 (random) to about −2.9, close to the hand-written rule (−2.4). The learned matrix looks like:

Read it: the "right" row has weight +8 on obs, so when the target is to the right (obs > 0), "right" wins. The "left" row is the mirror image. Nobody wrote that rule; it was learned from reward. That is the entire magic, scaled up from 6 weights to 84,000.

PPO in pseudocode

Analogy

A coach watches 4096 players each attempt 24 moves. They note which moves beat expectations, then give every player the same small correction. "Small" is the clip: never change their technique so much at once that they forget how to stand.

Lesson 3

JAX crash course: the five ideas you need

Every line of the environments is JAX. Learn five ideas and the code stops looking alien.

Goals

  • Recognize jp, .at[].set(), PRNG key splitting, jp.where, jit and vmap in the repo.
  • Know why there are no Python ifs on array values inside the env.

Why JAX?

JAX is NumPy that can (1) compile your function for the GPU (jit), (2) batch it automatically over thousands of inputs (vmap), and (3) take gradients (training uses this). In the repo, import jax.numpy as jp, so jp is "numpy, but JAX".

Now spot them in the real environment

Idea 2 (immutable update): randomizing the robot's start position in reset():

Idea 4 (jp.where instead of if): the random shove in step(). Every env computes a push every step, but only the ones whose timer says "now" actually use it:

Idea 5 (vmap): domain randomization gives every one of the 4096 envs its own friction and mass:

The classic trap

Inside a jitted function, if state.info["push_step"] > 5: crashes (ConcretizationTypeError). The value is a traced array whose number isn't known at compile time. Use jp.where. But cfg.push_config.enable is a plain Python constant from the config, known at compile time, so mixing it in is fine.

Why immutable?

Same reason you'll see state.replace(data=data) everywhere: JAX functions must be "pure" (output depends only on input) so they can be compiled and vmapped. Instead of changing things, you return new versions.

Try it
  1. In jax_basics.py, replace the first jp.where with a Python if target > x: and run it. Read the error message. You'll meet it again someday.
  2. Change 4096 to 100,000 keepers. Still fast? That's vmap.

2. Hands-on: a pendulum with a PD motor

The most important observation in this lesson

We asked for 0.8 rad and got about 0.70 rad. Gravity pulls the pole down, and a PD controller only produces torque when there is an error, so it settles where kp × error balances gravity. On the T2 this is everywhere: legs carrying body weight, arms hanging. The policy learns to command whatever targets produce the posture it wants. That's one reason a learned policy beats hand-written joint targets.

3. The real T2 model

Motors in the T2 standing model (the default classes set gains per joint group):

Sensors the policy's observation is built from:

qpos and qvel: the state vectors

qpos (nq = 38) = [ x, y, z, qw, qx, qy, qz, joint_0 … joint_30 ] └ trunk position ┘└ orientation ┘ └ 31 joint angles ┘ qvel (nv = 37) = [ vx, vy, vz, wx, wy, wz, jointvel_0 … jointvel_30 ] (orientation: 4 numbers in qpos but 3 in qvel) soccer model adds the ball's free joint: nq = 45, nv = 43

That's why the code is full of qpos[7:] (joint angles), qvel[6:] (joint velocities), qpos[2] (trunk height) and qvel[0:2] (horizontal speed).

MJX: thousands of robots on one GPU

MuJoCo + JAX's vmap = MJX. This is where "9 minutes to train" comes from.

Goals

1. Same pendulum, 1024 copies

The key line is jax.vmap(mjx.step, in_axes=(None, 0)): "the model is shared (None), the data has a batch dimension (0)". Domain randomization (Lesson 9) goes one step further and batches some model fields too, so each env gets its own friction and mass.

(Notice the gravity offset from Lesson 4 again: target −1.0 rad, settled at −0.886.)

2. jax vs warp backends

3. The arithmetic you should be able to do

throughput ≈ 150,000 – 200,000 env-steps/s (4096 envs, warp, big GPU) 100 M steps ÷ 180,000 /s ≈ 555 s ≈ 9 minutes of wall-clock time 100 M steps × 0.02 s = 2,000,000 s ≈ 23 days of robot experience
Why a GPU

A CPU is a few very smart workers. A GPU is thousands of simple workers. Stepping 4096 independent robots means doing the same math on 4096 different sets of numbers, which is exactly what thousands of simple workers are good at.

Lesson 7

Observation design: what the robot is allowed to know

The policy can only react to what's in the observation. Too little and it's blind; anything the real robot can't measure and it won't deploy.

Goals

  • Know every slice of the 102-dim standing observation and the 7 soccer additions.
  • Understand projected gravity, relative joint positions, last action and noise.
  • Apply the "deployable only" rule to a goalkeeper.

1. The 102 numbers

2. Why each piece is there

PieceWhy the policy needs it
Projected gravityThe world's "down" vector (0, 0, −1) expressed in the robot's own frame. Upright → (0, 0, −1). Tilted by θ → the horizontal part has length sin θ. It's the IMU's tilt reading, and the main "am I falling?" signal.
Joint pos − defaultCentered numbers: 0 means "at the standing pose". Networks learn better from small, centered inputs.
Last actionMotors lag their targets, so the policy needs to know what it already asked for. It's also needed for smooth commands.
NoiseReal sensors are noisy. Training with noise means the policy doesn't trust any single reading too much.

The trainer also normalizes observations (normalize_observations=True): a running mean and standard deviation per dimension, so joint velocities (tens of rad/s) and gravity (≤ 1) reach the network on similar scales.

3. Soccer adds 7 (→ 109)

4. The deployable-only rule

The rule

The final policy runs on the real robot's computer (a Jetson). It can only use what the robot can measure: IMU + joint encoders + camera detections. The simulator knows the true ball position, but the real robot never will. A policy trained on the truth may completely fail on the real camera.

Allowed during development: it's fine to start with perfect ball information to learn the motor skill, then switch to realistic perception as a later stage. The repo even has a debug switch for this (perception.perfect). Just don't deploy that version.

What a keeper probably needs

  • Everything from the 102 (balance).
  • Ball position and velocity relative to the robot. Velocity is what tells you where the shot will cross the line. The 109-dim soccer obs has no ball velocity, because the striker can live without it; a keeper can't.
  • Own-goal position relative to the robot (where am I in my goal?).
Try it

Write down your keeper's observation as a table: slice, dims, contents, where it comes from on the real robot (IMU? encoder? camera?). Mark anything that's "sim-only". Keep this table; it goes in your design doc in Lesson 13.

Lesson 8

Reward design: saying what you want, precisely

The policy will do exactly what you reward, including things you didn't mean.

Goals

  • Read the weighted-sum reward and its terms.
  • Understand the "falling is cheaper than living" trap and its fix.
  • Use potential-based shaping, and know why it can't be farmed.
  • Sketch keeper rewards.

1. The total reward is a weighted sum

Each term is a raw measurement, and its scale (in the config) sets its sign and importance. Most standing terms are penalties (negative scales):

2. The trap: when falling is the smart move

This really happened in this project (the experiment log's stage 0.5). Suppose all the small penalties add up to about −0.5 per step on average:

stay alive 1000 steps: 1000 × (−0.5) = −500 fall at step 10: 10 × (−0.5) + (−200) = −205 ← PPO prefers this!

The optimizer isn't broken. It found the best answer to the question you actually asked. This is reward hacking. The repo's fix is a positive survival reward, +0.06 per step alive: over a 2000-step episode that's worth +120, so living beats dying.

Rule of thumb

Before training, do this arithmetic: what's the total reward of (a) standing still for the whole episode, (b) falling immediately, (c) the behaviour you want? (c) must clearly beat both.

3. Shaping: rewarding progress

A "+1 per save" reward is sparse. A random policy almost never saves, so there's nothing to learn from (you saw this in Lesson 1). Shaping adds dense hints. The safest kind is potential-based: pay the change in a distance.

Σ over the episode of (d_prev − d_now) = d_start − d_end → only the start and end matter. Walking back and forth earns exactly nothing, so it can't be farmed.

4. Debugging rewards

Every term is logged separately as reward/<name> in the metrics. When behaviour is wrong:

  1. Look at which terms dominate the total. Is it the one you expected?
  2. Check units: a squared velocity in m²/s² and an angle in rad² can differ by 100×.
  3. Change one scale at a time and compare runs.

Lesson 9

Sim-to-real: making it survive reality

The simulator is always wrong in small ways. The job is a policy that doesn't care.

Goals

  • Name the sources of the sim-to-real gap.
  • Know the defences: noise, domain randomization, disturbances, perception modelling.
  • Learn from the repo's "100 % in sim, falls in 1 s" bug.

1. Where sim and reality differ

  • Masses, centres of mass, friction, motor strength and delay are never exactly right.
  • Sensors are noisy and late; the camera misses the ball sometimes.
  • People bump the robot; the floor isn't perfect.

2. The defences used in this repo

DefenceWhat it doesWhere
Observation noiseUniform noise on every sensor readingnoise_config in t2_stand.py
Domain randomizationEach env gets its own floor friction U(0.7, 1.0), trunk mass ±2 kg, centre of mass ±3 cmt2_rl/randomize.py
PushesRandom velocity kicks every 3–6 s (v3/v4)push_config
Clash impulsesShort 40–120 N bursts on shoulders/elbows/trunkclash_config (v4)
Virtual perceptionCamera field of view (87°×58°), 90 % detection up to 7 m, ~120 ms delay, noise growing with distancet2_soccer.py perception block
ball noise σ = 0.149 + 0.124 · d at 2 m: σ ≈ 0.40 m at 5 m: σ ≈ 0.77 m

That's a lot of noise. A keeper that only works with perfect ball information won't survive a real camera, which is why realistic perception gets its own stage.

3. A true story from the repo

"100 % success" that fell in one second

v1 and v2 scored 100 % survival in training. But the ported environment had a bug: it reset the robot's root velocity to zero every step instead of only during pushes. The policies learned to balance in a fake, heavily damped world. In real momentum physics, both fell within about 1 s, even without a push. v3 fixed the physics and retrained.

Lessons: (1) great training numbers only mean "great in this simulator"; (2) test in a different setting than you trained in (the repo's push_test --engine cpu runs plain MuJoCo for exactly this reason).

4. How the policy reaches the robot (future stage)

trained weights (.pkl) → export to ONNX → C++ behaviour-tree node on the T2's Jetson, 50 Hz gated by the team brain (Robotedge-5v5-RCAP2026): e.g. decision == 'rl_goalie_save' → run the keeper policy

Not built in the repo yet (it's the roadmap's last stage). It's the reason for the deployable-only rule.

Lesson 10

The training script, top to bottom

scripts/train_stand.py wires your environment into brax's PPO and writes everything to logs/.

Goals

  • Follow the flow: CLI flags → env → network → PPO → checkpoints.
  • Read a training log line and know what "good" looks like.
  • Know which hyperparameters to touch (few) and which to leave alone (most).

1. The flow

pixi run train --env v4 --impl warp ... │ ├─ ENVS["v4"] → (T2StandV4, default_config_v4) ├─ env = T2StandV4(config) → loads XML, puts it on the GPU ├─ network_factory → MLP 256/128/128, ELU, tanh-normal actions ├─ ppo_train.train(...) → brax's PPO loop: │ wrap_for_brax_training(env) + domain_randomize → 4096 envs, each different │ rollout → GAE → 20 gradient steps → repeat │ every eval: progress_fn (prints + metrics.jsonl), policy_params_fn (checkpoint) └─ save params_final.pkl

4. Reading the log

Every evaluation (20 per run by default), progress_fn prints a line like this:

Lesson 11

Tools & the A100 cluster

pixi for the software, SLURM for the hardware. Neither is hard once you see what problem it solves.

Goals

  • Know what pixi, pixi.lock, CUDA, WSL2 and wandb are for.
  • Know how a cluster job flows: VPN → SSH → login node → sbatch → queue → A100.
  • Know the five SLURM commands and the cluster's house rules.

1. pixi: the exact same software everywhere

The training stack is a tower of tightly coupled versions (Python 3.12, jax 0.11.1 with CUDA 12, mujoco 3.12.0, warp 1.16.0 (1.17 breaks!), brax 0.14.2…). pixi pins all of them:

  • pixi.toml: what you want (like requirements.txt, but with Python itself and named tasks).
  • pixi.lock: the exact resolved versions. pixi install on any machine gives you identical software.
  • pixi run train ... = run the train task (scripts/train_stand.py) inside that environment.
Linux only

pixi.toml says platforms = ["linux-64"]. On Windows you'd need WSL2 (Linux inside Windows), and even then your laptop's GPU is too small. The cluster is Linux, so it just works there.

House rules

  • VPN first, always. SSH is blocked without it.
  • Never train on the login node. It's shared; sysadmins will notice.
  • Compute nodes have no internet, so wandb runs offline and you sync later from the login node.
  • Storage: /scr/user/<you> is fast but not backed up (files idle for 90 days get deleted); /home is backed up but only 100 GB.
  • Account: you need a full account. A limited one can't use gpu-a100. Check with account-info.

3. wandb (Weights & Biases)

A website that plots your training curves live. On by default in the trainer. For your first runs, pass --no_wandb (or let the cluster script use offline mode) so you have one less thing to set up.

Lab 1

Your first training run (on the A100)

Goal: retrain the v4 standing policy from scratch, evaluate it, watch the video. It's nothing new; the point is to see the whole machine work once with your own hands.

Before you start

  • Full DICC account + VPN working (Lesson 11).
  • Quizzes 0–11 done, or at least Lessons 6 and 10 understood.

Part A: get onto the cluster and build the environment

  • Connect the VPN, then SSH in: ssh <username>@login01.dicc.um.edu.my
  • Check your account: account-info. It must be a full account with access to gpu-a100.
  • Clone into scratch:
    cd /scr/user/$USER
    git clone https://github.com/f4ww4z/t2-mujoco-rl-playground.git
    cd t2-mujoco-rl-playground
  • Build the environment (installs pixi if needed, creates logs/slurm/, about 4–8 GB download). DICC asks for this inside a small CPU allocation:
    salloc --partition=cpu-epyc --nodes=1 --ntasks=1 --cpus-per-task=4 --mem=16G --qos=short --time=01:00:00
    ./hpc/setup.sh then exit.
    If the compute node can't download (DNS/timeout), run ./hpc/setup.sh on the login node instead; it's only a download.
  • Smoke job on an A100 (proves driver + CUDA + physics):
    sbatch --job-name=t2_smoke --qos=short --time=00:30:00 hpc/job.sbatch smoke-all
    squeue --me → wait for it to finish → tail logs/slurm/t2_smoke_*.out
    Success: the log ends with [job] task=smoke-all exited with status 0, and gpu-check reports jax … gpu.

Part B: train, evaluate, watch

  • Submit your first training run (100 M steps; around 10–20 min of training on an A100 plus queue time):
    sbatch --qos=short --time=00:55:00 --job-name=my_first_v4 hpc/train.sbatch train --env v4 --num_envs 4096 --num_timesteps 100000000 --run_name my_first_v4
    The script adds --impl warp --wandb_mode offline for you.
  • Watch it learn: tail -f logs/*my_first_v4*/train.log. Write down avg_episode_length at each eval. Does it climb toward 1000?
  • Evaluate survival (200 episodes, with pushes):
    sbatch --qos=short --time=00:55:00 hpc/job.sbatch play --env v4 --checkpoint logs/<your_run>/params_final.pkl --episodes 200
    Note --env v4: play defaults to v1, and a mismatched env gives nonsense.
  • Render a video (headless rendering works on the cluster):
    sbatch --qos=short --time=00:55:00 hpc/job.sbatch play --env v4 --checkpoint logs/<your_run>/params_final.pkl --video
    It writes rollout.mp4 next to the checkpoint.
  • Download and watch (on your laptop, VPN on):
    scp <username>@login01.dicc.um.edu.my:/scr/user/<username>/t2-mujoco-rl-playground/logs/<your_run>/rollout.mp4 .
  • Back up runs you care about: ./hpc/backup_logs.sh (copies logs/ from scratch to home).

Lab 2

Design your goalkeeper

Your idea: block ground shots with the legs, take up a good position based on where the ball is, and never fall over. Here is how to turn it into an environment you write yourself.

Goals

  • Use physics arithmetic to set priorities.
  • Write a one-page design doc: obs, action, reward, reset, termination, curriculum, success metric.
  • Start your own environment from a skeleton, in your own repo.

1. Physics first: what matters most?

goal mouth: 2.6 m wide · standing T2 covers roughly 0.4 m of it (≈15 %) ground shot 5 m/s from 6 m → reaches the line in ≈ 1.2 s minus camera delay ≈ 0.12 s → ≈ 1 s to react; a humanoid side-step covers maybe 0.3–0.5 m ball diameter 0.22 m · v4 stance ankle gap ≈ 0.16 m

Conclusions (estimates, so verify them in sim):

  1. Positioning beats reaction. Standing on the ball–goal line means most straight shots hit you with no fast motion at all.
  2. "Closing the legs" already happens in a normal stance: the ball is wider than the gap. Reaching wider with a leg is what opens the gap. That's a trade-off the policy will have to learn.
  3. Ball velocity is essential: without it the keeper can't know where the shot will cross the line.

2. The positioning target

A classic keeper rule: stand on the line from the ball to the centre of your goal, a short distance r in front of the goal line.

target = goal_centre + r · (ball − goal_centre) / |ball − goal_centre| (r ≈ 0.5–1.0 m)

Reward idea (potential-based, Lesson 8): d_prev − d_now where d = distance from the keeper's trunk to target. As the ball moves, the target moves, and the keeper learns to shadow it.

3. The curriculum (one skill at a time)

StageResetRewardsDone when
K0 stand in goalKeeper at the goal mouth facing the field, no ballstanding terms + survivalsurvives 20 s with pushes
K1 positioningBall placed and slowly moved around the defending half+ positioning shaping, face the balltracks the target within ~0.2 m
K2 slow ground shotsAfter a random delay, ball shot along the ground (no upward velocity) at 1–2 m/s toward a random point in the mouth+ save, − conceded, + intercept shapingsave rate clearly above "standing still"
K3 faster shotsRaise speed step by step to 5–6 m/ssamesave rate on a fixed shot grid
K4 real perceptionCamera field of view, delay, noise+ head trackingsave rate holds
K5 (later) diveNew termination rules + get-up-research

Start K0–K3 with perfect ball information (true position + velocity), so you're learning the motor skill. K4 handles realistic sensing as its own problem.

4. Your design doc (fill this in)

Template
  1. Skill: one sentence. (e.g. "Stay on the ball–goal line 0.8 m out and block ground shots up to 3 m/s without falling.")
  2. Observation table: slice · dims · content · real-robot source · sim-only?
  3. Action: 31 joint offsets? What action_scale? (Standing uses 0.5; bigger leg reaches may need more.)
  4. Reward table: term · formula · scale · why. Then the arithmetic: total for (a) stand still, (b) fall immediately, (c) the behaviour you want.
  5. Reset: where the keeper and ball start; how shots are generated; what is random.
  6. Termination: what ends an attempt? Does a shot ending (save/goal) end the episode, or does a new shot start?
  7. Success metric: e.g. save rate on a 9-point grid of shot targets × 3 speeds, 32 trials each.
  8. Deployment note: behaviour-tree node name (e.g. RLGoalieSave), gating key (e.g. decision == 'rl_goalie_save'), deployable observation list.

This goes in your own repo. It's a skeleton with TODOs, not a solution: it shows the shape (same as Lesson 6), and the design decisions are yours.
